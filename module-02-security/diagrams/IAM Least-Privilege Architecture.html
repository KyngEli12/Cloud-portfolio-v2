IAM Least-Privilege Architecture

Module 02 — Security

Least-Privilege IAM Architecture

How to design AWS access so every identity — human or machine — holds only the permissions it needs, enforced at every layer from the org root to the resource policy.

How it works — step by step

Step 01

SCP sets the ceiling

Service Control Policies at the org root deny the most dangerous actions for every account — disabling CloudTrail, creating root access keys, leaving the approved region. Even an account admin can't override these.

Deny: cloudtrail:StopLogging
Step 02

Developer assumes a role

No long-lived IAM user access keys. The developer calls sts:AssumeRole to get a temporary credential scoped to AppDeployRole. MFA is required. The session expires in one hour.

sts:AssumeRole + MFA
Step 03

Permission boundary caps the role

A permission boundary is attached to AppDeployRole. Even if an admin accidentally adds a wildcard policy to the role later, the boundary caps what it can actually do. Two locks instead of one.

iam:PutRolePermissionsBoundary
Step 04

Resources enforce their own policies

Each resource — S3, Lambda, DynamoDB — has its own resource-based policy allowing only AppDeployRole, only the specific actions needed. If the role is somehow compromised, blast radius is limited to what each resource explicitly allows.

s3:GetObject · dynamodb:Query
Step 05

Lambda has its own execution role

The function doesn't inherit the developer's role. It runs under LambdaExecRole — a separate least-privilege role created just for what that function needs at runtime. Roles are never shared between workloads.

Separate role per workload
Step 06

CloudTrail logs everything

Every API call is logged to an immutable S3 bucket. CloudWatch Alarms fire on suspicious patterns — root login, console sign-in without MFA, policy changes. The SCP prevents anyone from turning CloudTrail off.

cloudtrail:CreateTrail

Decision log

Decision Why Trade-off Tag
No long-lived IAM user keys Long-lived keys are the #1 cause of AWS breaches. Temporary credentials via STS expire automatically — no manual rotation needed. Developers need to re-authenticate hourly, adding minor friction. Security
Permission boundaries on all roles A second guardrail independent of the identity policy. Even a misconfigured policy escalation can't exceed the boundary. More IAM objects to manage; boundaries must be updated when the role legitimately needs new permissions. Security
Separate execution role per Lambda Shared roles mean a compromised function can affect every other workload using that role. Isolation limits blast radius. More roles to maintain at scale; can be managed with IaC (CDK/Terraform). Design
SCP denies CloudTrail disable An attacker's first move after getting in is often to disable logging. Making it org-level undeniable removes that option entirely. No trade-off — there is no legitimate reason to disable CloudTrail in production. Security
Resource policies on S3 and DynamoDB Defense in depth — even if IAM is misconfigured, the resource won't serve data to an unexpected principal. Two independent checks. Policy changes must happen in two places (IAM + resource) when access requirements change. Ops
Explicit Deny on s3:DeleteObject Accidental deletions are irreversible without versioning. An explicit deny blocks it entirely for all principals, including future admins. Cleanup operations require a deliberate policy change — intentional friction. Security
