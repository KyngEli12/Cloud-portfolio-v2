Cache-Aside Architecture

How a read request moves through ElastiCache Redis, DynamoDB, and Aurora Serverless v2 — and what changes when the cache is warm vs. cold.

Request Flow

Cache Hit (warm path)

  1. Client sends read for productId
  2. ElastiCache Redis checks key — found
  3. Return cached value immediately
  4. DynamoDB never touched

Cache Miss (cold path)

  1. Client sends read for productId
  2. ElastiCache Redis checks key — not found (TTL expired or first request)
  3. Application reads from DynamoDB
  4. Application writes result back to cache with TTL
  5. Return value to client
Decision Log
Decision Choice Reasoning / Trade-off
Cache pattern Cache-aside (lazy loading) WHY Application controls cache population — only data actually requested gets cached. No wasted cache memory on cold data.
TRADE-OFF First request always pays the miss penalty. Write-through would keep cache warmer but adds write complexity.
Cache store ElastiCache Redis OSS Serverless WHY Managed Redis with no cluster sizing decisions. Scales to zero when idle — no cost between sessions.
TRADE-OFF Serverless has higher per-request cost at sustained load vs. a provisioned cluster. Acceptable for portfolio/low-traffic use.
Primary data store DynamoDB (free tier) WHY Single-digit millisecond reads, no server management, free tier covers portfolio workload. Partition key on productId enables direct key lookups that match the cache pattern exactly.
TRADE-OFF No joins. Complex relational queries require Aurora. Chosen intentionally — product catalog is document-shaped, not relational.
Relational store Aurora Serverless v2 (deferred) WHY Needed for relational workloads (orders, user accounts) that DynamoDB handles poorly. Serverless v2 scales to zero ACUs when idle.
TRADE-OFF ~$0.20/session cost to spin up. Deferred to dedicated session to control spend and document the Aurora-specific setup separately.
TTL on cache keys 5 minutes WHY Product catalog data is mostly static. 5 min balances freshness vs. cache hit rate for a demonstration workload.
TRADE-OFF Stale reads possible within the TTL window. Production systems would tune per data type or use explicit invalidation on writes.
Cost control Delete ElastiCache after each session WHY Serverless Redis still incurs idle cost (~$0.50–2/mo) even with no traffic. DynamoDB and S3 stay within free tier.
TRADE-OFF Cluster must be recreated each session. Acceptable in a portfolio context; production clusters run continuously.
